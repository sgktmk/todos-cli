# 実装上の決定事項

要件定義書 v0.2 の「25. 未確定事項」および実装時に判断が必要だった点について、
採用した仕様とその理由を記録する。変更したい項目があればここを起点に議論する。

## 技術スタック

**決定**: Python 3.9 以上・標準ライブラリのみ。外部パッケージ依存ゼロ。

理由:

- TUI (`curses`)、JSON (`json`)、日付 (`datetime`)、全角幅計算 (`unicodedata`) が
  すべて標準添付で、追加インストールが要らない。
- macOS / 主要な Linux ディストリビューションには python3 が入っている。
- インストールは「1ディレクトリをコピーして起動スクリプトを置く」だけで済む
  （`install.sh`）。ビルドもリリース資材も不要。

`pyproject.toml` も同梱しているため `pip install .` / `pipx install .` でも入る。

## 25.1 Tomorrow への配置条件

**決定**: 期日が明後日（実行日 +2 日）のタスクを Tomorrow へ置く。

要件 11.2 で「期限日の前日から Today へ配置する」と決まっているため、
Today には「期限切れ・本日・明日」が入る。その1日先、つまり
「明日のうちに着手しておきたいもの」が Tomorrow に相当すると解釈した。

判定は Today → Tomorrow → InWeek → ParkingLot の順に評価する。
そのため当週日曜より先が期日でも、明後日が期日なら Tomorrow が優先される
（例: 土曜に実行した場合の月曜期日）。

手動で Tomorrow へ移したタスクも、要件 11.6 のとおり次回の再配置で再評価される。

## 25.2 同一セクション内の並び順

**決定**: 期日昇順 → ステータス優先度 → 元の記述順。

- 期日なしは最後に回す。
- ステータス優先度は 要返答 → 進行中 → 未着手 → 回答待ち → 保留 の順。
  - 要返答は自分の返答で相手が止まっているため最優先。
  - 回答待ちは自分が動けないので未着手より下。
  - 保留は着手対象外なので最下位。
- 同着なら元の記述順を保つ（安定ソート）。

要件で確定していた「同一期日なら要返答を通常タスクより優先」を満たす。

## 25.3 アーカイブ見出しの日付

**決定**: アーカイブ実行日を使用する。利用者への確認は行わない。

完了日時を保持しない方針（要件 22.3）のため実際の完了日は復元できない。
実行日なら確認なしで機械的に決まり、要件 16 と同じ「候補であって記録ではない」
という位置づけで一貫する。archive.md 内では新しい日付が上に積まれる。

## 25.4 アーカイブ提案の条件

**決定**: 未アーカイブの終了タスクが1件でもあれば提案する。ただし提案するのは
`todos list` の実行時と TUI 起動時のみ。

- 終了日時を持たないため「前日以前に終了したか」は判定できない。
- 一方で `todos done` の直後に毎回アーカイブを提案されると煩わしいので、
  一覧を眺める文脈に限定した。
- `--no-prompt`、`--json`、非対話実行時は提案しない（要件 20.2）。
- 明示的に実行したいときは `todos archive` を使う。

## 25.5 タスクの指定方法

**決定**: 「一覧上の表示番号」または「タイトルの部分一致」。

- 表示番号は `todos list` に表示される 1 始まりの通し番号。
  子タスクも含めてファイル内の出現順に振られる。
- 数字のみの指定は表示番号、それ以外はタイトルの部分一致として扱う。
  完全一致するタスクがあれば部分一致より優先する。
- `--section` を併用すると候補を絞れる。
- 複数該当した場合、対話実行なら候補を提示して選ばせる。
  非対話（`--json` 実行やパイプ経由）なら変更せず終了コード 2 で返す（要件 13）。
- 表示番号はファイルが変わると振り直される。番号を控えて使い回さない。

## 25.6 TUI の画面仕様

`docs/tui.md` に分離した。

## その他の実装判断

### 日付更新の検出方法

状態ファイルを持たない方針（要件 22.3）のため「前回いつ実行したか」を記録できない。
そこで **現在の配置と、いま計算した配置が食い違うタスクが1件でもあれば
再配置が必要とみなす**。日付が変われば自然に食い違いが発生するため、
要件 12.2 の目的は満たせる。

副作用として、手動で別セクションへ移したタスクがあると毎回提案が出る。
要件 11.6 が「手動移動も再評価対象」と定めているため、仕様として許容する。
提案を止めたいときは `--no-prompt` を使う。

### 未知の見出しの扱い

`## Today` などの既知セクション以外の見出しが現れた場合、その配下は
**解析せずそのまま保存する**。推測で書き換えない方針（要件 22.4）を優先した。
ただし配下にタスク行が埋もれている場合だけは「管理対象外」として警告する。
ファイル冒頭の `# tasks` のようなタイトル行は前書きとして扱い、警告しない。

### 解釈できない期日の扱い

`（〜来週の火曜）` のように期日マーカーはあるが日付として解釈できない記述は、
**タイトルから切り出さずそのまま残す**。警告は出すが自動修正は提案しない。
切り出してしまうと利用者が書いた情報が消えるため（要件 22.4）。

日付として解釈できても正規形式でないもの（`（〜2026-07-31）` など）は
`todos validate --fix` で正規形式へ書き換える。

### 期日と判定する条件

タイトル中の日付を誤って期日と解釈しないよう、次のいずれかがある場合だけ
期日として扱う。

- 括弧で囲まれている（`（〜2026/07/31）`、`（2026/07/31）`）
- チルダが付いている（`〜2026/07/31`）
- ラベルが付いている（`期限:`、`締切`、`due:` など）

「2026/07/31の定例会」のような記述はタイトルの一部として残す。

### タグの抽出位置

タグは **行末に連続している `#xxx` のみ** をタグとして扱う。
タイトル中の `#` は本文の一部として残す。要件 6.1 の並び順に従った記述を前提とし、
誤検出でタイトルを壊さないことを優先した。

### インデントの正規化

書き戻し時、子タスクと詳細文のインデントは 1 段 2 スペースに揃える。
4 スペースで書かれていても解析はできるが、出力は 2 スペースになる。

### ファイル書き込みの順序

アーカイブ実行時は archive.md を先に書き、成功後に tasks.md を書く。
途中で失敗した場合、両方に同じタスクが残る（重複）ことはあっても、
どちらからも消える（消失）ことはない。

書き込みはすべて同一ディレクトリ内の一時ファイル経由で行い、
`os.replace` で原子的に差し替える（要件 22.4）。

### East Asian Ambiguous 文字の幅

`…` などの曖昧幅文字は既定で 1 桁として扱う。日本語環境で罫線がずれる場合は
環境変数 `TODOS_AMBIGUOUS_WIDTH=2` を指定する。

### tasks.md の探索順

1. `--dir` オプション
2. 環境変数 `TODOS_DIR`
3. カレントディレクトリから上位へ `tasks.md` を探索
4. 見つからなければ `~/todos`

3 があるため、プロジェクトごとに tasks.md を置いてその配下で作業できる。

### 対応環境

- OS: macOS / Linux（要件 22.7）
- 端末: UTF-8 かつ curses が使えるもの（xterm 系、iTerm2、Terminal.app、
  GNOME Terminal、tmux など）
- Windows は未対応。WSL 上での動作は Linux と同じ扱い。
